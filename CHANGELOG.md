# Changelog

## 0.5.0

**Upgrading from 0.4.0**

- Update: run `claude plugin update signoff@signoff`, then `/reload-plugins`, and restart each Claude Code session that was open during the update: one started on 0.4.0 keeps that version's monitor until then. Then restart a running inbox with `signoff inbox stop` and open it again. An inbox keeps running through an update, and one from 0.4.0 does not know the new round keys. With the macOS app, quit the app before you stop the inbox, run `brew upgrade --cask signoff`, start a new Claude Code session, then open the app: it starts the new inbox.
- The Waiting hint `off` now only hides the count: the mod still hands over your messages from the inbox.
- Removed: the MCP server, the plugin's monitor, the panel's App button and `signoff inbox open --app`, answering from a notification, the Vulnerabilities section, and the app's menu bar panel. The mod now hands over your messages from the inbox, so `/restart` works. A click on the menu bar icon opens the window.
- New, and off by default: Plan review. To review a plan in Signoff, set Plan review to `inbox` in `/config`.
- Claude Code 2.1.271 or newer is needed.
- Rounds and answers files from 0.4.0 still load, because the file formats only grew.

**All changes**

- **Park a round, and see past decisions in the inbox:** each round row in the inbox list (and the macOS app) ends in a **Park** button. A parked round leaves Waiting on you for **Parked**, a section under Answered that starts closed. It counts nowhere (the tab title, the sidebar, the band and panel, the app's badge) until you press **Back** on its row. **Back** puts the round into Waiting on you again, as **Run ended** for 14 days when its run has ended, and sends no app notification. `state.json` gains `backs`, the number of times Back raised the count, and readers that do not know it skip it. Parking keeps only the round file's path and the times, in `parked.json` in the Signoff home. The round's files and its run stay as they were, and its row says **Agent waiting** while that run still runs. Each project in the sidebar links to its **Past decisions**, the read-only page `signoff --history` shows, now also inside the inbox and its app window.

- **A picker in `/config`, and the Claude Code floor:** Waiting hint is now a picker in `/config`. A Claude Code before 2.1.271 no longer loads the plugin.
- **Over SSH or in a devcontainer:** `--port <n>` on a run or `--history`, or the `SIGNOFF_PORT` environment variable, puts Signoff on one port you choose (1024 to 65535). The flag wins. `SIGNOFF_PORT` also sets the inbox's port, kept in `inbox.json` as before. A tunnel (`ssh -L`, `LocalForward`, VS Code's Ports tab) is then set up once instead of for every run. Signoff still listens on `127.0.0.1` only, and the port stays random unless you set one. Any process on the machine can take a free port first, and a page served there can leave a service worker in your browser that sees later Signoff pages on that port. Pick a port no other web app has used in that browser (see `docs/security.md`). A bad value exits 1 with one line on stderr and nothing on stdout. So does a port another program listens on. Signoff looks for that with a connection to `127.0.0.1:<port>` before it binds, which is best effort, and on macOS it also catches a listener on every address. An `inbox serve` that stops there leaves no `inbox.lock`. In an SSH session (`SSH_CONNECTION` or `SSH_TTY` set) with no `BROWSER` set, a run and `signoff inbox open` open no browser and print the start link, as with `--no-open`. They add the `no browser opened` line, which the agent uses to hand you the link. VS Code's Remote - SSH terminal sets a `BROWSER` that opens the link on your computer. `signoff inbox open` on a taken port now says at once that the inbox did not start, not after 15 seconds. Open the link with `127.0.0.1`, as printed, because a browser may try `localhost` as `::1` first. The page, the inbox and the past-decisions page now also answer to `localhost:<port>`, because a forwarded port is often opened that way. A save must then come from that same name (`Origin`). Every other host name or port, and a request with two Host headers, gets 403. The start link Signoff prints stays `http://127.0.0.1:…`. Known limit: over SSH a row in the mod's panel opens nothing you can see, as on a machine without a browser. On Windows Signoff no longer sets `SO_REUSEADDR`, which there would let a second program bind the same port. `docs/running.md` has the steps.

- **The mod in the desktop app and VS Code:** tried on macOS in the desktop app's Code tab and in the VS Code extension's own panel. The line above the prompt, the panel, the notice and the status line show there, and the mod ran Signoff's command (`signoff inbox home`). The README's table says so. Both send `session.start` as not interactive, so the mod starts looking at the band's first drawing, as it already did after a reload. No code change.
- **`/signoff:demo` and README notes:** `/signoff:demo` writes a small synthetic round in a temporary folder outside your project, runs Signoff on it, and gives you the command to remove the folder. The model never starts it. Only you can, by typing it. Both READMEs now say to use Claude Code from the stable channel or newer, and that auto-update is off by default for a third-party marketplace. The README's browser table says Safari and Firefox were tested on macOS (a Done from the inbox page).
- **Unticking every recommended option is an answer:** a recommended `many` item whose every option you unticked now counts as answered, so the panel no longer lists it.
- **A phone's first screen:** on a phone in Focus, an item now shows its question, the agent's recommendation and cost, its commands, and then its pictures as thumbnails. A tap opens a thumbnail full size. The first option now shows without scrolling. A picture you can mark starts small beside its caption, and **Larger** gives it the full width to draw on (**Smaller** takes it back). On a phone, in Focus or not, the header keeps the title beside the project's mark. Its buttons sit on a row below, and there is no progress pill, because the bar says which round waits. The bar at the foot takes two rows, or three when the save state needs a line of its own, as after a reload. On wider screens the opening time also sits on a line of its own. When the round's title would get less than 260 px, the header's buttons move to a second row, right-aligned, instead of squeezing the title.
- **One-line fields in the Markdown copy:** a title, group, option label, unit, caption or attachment name that holds a CR, U+2028, U+2029, NEL, VT, FF or FS/GS/RS character no longer splits its heading or list line in the copy. Each such break shows as a space. Rounds with such text still load.

- **A round's age:** a round's page says when the round was asked (`Opened <date> · 3 days ago`) under the project's name in the header. The time is the round file's time, which a new run on the same rounds keeps. An open round 2 days old or more also says **Open 2+ days** there and, at the top of the round, that its questions can be out of date. Its row in the inbox gets the same words, and its open row says how long. The row's time and order still follow the run's start. No file format changes.
- **A todo file of your choice:** a `todo` key in a project's file in the Signoff home (`projects/<id>.json`) names the project's todo file, as a path relative to its root. Use it when a project keeps its list in a file other than `_bmad-output/todo.md`, `TODO.md` or `todo.md`. The inbox then reads that file alone, and it must be a file inside the root (links followed). Otherwise the inbox lists the project with a fixed error and reads none of the three. The hooks never write the key. You add it by hand, as `docs/inbox.md` says. Without it nothing changes.
- **Done per round:** the `signoff` skill tells the agent that it can run each round alone in the background (`signoff <folder>/round-NN.json`) when it can act on one round before you answer the others. Each run wakes the agent at its own Done. A round that depends on another's answers is run alone too while others of the folder are open. No code change.
- **No App button:** the panel's rows no longer have an App button, and the mod no longer reads the app's `Info.plist`. Each row opens its question in the browser, as before. `signoff inbox open --app` is gone. It is a usage error now, exit 1, with nothing run. The control socket's `app_target` and `app_open` are gone too, and they get the unknown-request reply. The macOS app no longer asks the inbox for a question when it comes up. It shows its window as a Dock click does. An app from 0.4.0 gets no link for `app_open` and does the same. A 0.4.0 `signoff inbox open --app` still brings the app up, with no question.
- **Answered starts closed:** in the inbox list (and the macOS app), the Answered section is closed behind its heading, as a To do group is. A click opens it. A search opens it while a match is in it. A project picked in the sidebar opens it with that project's rows. The page's own reload keeps it as it was. Its rows are out of j, k and Focus while it is closed.
- **SIGTERM and SIGHUP stop a run as Ctrl+C does:** a run or a waiter that gets either one, from a closed terminal for example, now marks its entry in the Signoff home's `runs/` as ended and lets go of its round locks. It says `stopped` on stderr and exits 130, with nothing on stdout. Before, it died at once and left its entry without `ended`, so the inbox had only its process id to go by, which another process can get. This does not apply on Windows, where a stopped process gets no signal it can catch. A signal ignored at the start, as under `nohup`, stays ignored. `--history` and the `signoff inbox` commands are as before.
- **A project without git:** a folder that holds a `.signoff` folder is now a project root, as a folder with `.git` is, and the nearer one wins. Before, a session started in such a project's own folder was not noted. The inbox then showed no session row, band or todo for it, and a decisions folder outside its `.signoff` got no project name on the page. Now, in a git repo with a `sub/.signoff/` folder, a session started in `sub` belongs to `sub`, not to the repo, as the decisions under `sub/.signoff/` already did. So does a decisions folder elsewhere under `sub`. Its band counts `sub`'s rows, the inbox reads `sub`'s todo file, and messages on the repo's todo items no longer reach it. Likewise a `.signoff` folder in a parent folder without git (not the home folder) now takes in every folder below it that has no nearer `.git` or `.signoff`. A `.signoff` that is a file or a link marks nothing.
- **A stopped inbox costs a session no Python:** once the inbox had run, even with it stopped, the hooks started Python at every prompt and turn end. Now `hook.sh` looks at the time of `inbox.lock`, which a running inbox touches every two seconds. A lock a minute old or more counts as stopped, and the hooks stop before Python. A session's start, resume, clear or compaction still notes the session and hands over messages. While no inbox runs, sessions are not kept up to date. So after the inbox starts, a session's row can be stale until that session's next prompt, tool call or turn end. An inbox started by 0.3.0 does not touch the lock, so it counts as stopped. Restart it with `signoff inbox stop` and open it again.
- **Lighter hooks before the inbox has run:** when no inbox lock file exists in either place it can be (the macOS folder or the Linux one), the hook script now stops before it asks the system's name. This takes about 4 ms instead of 7 per hook event on a Mac. With the inbox running, the hook's Python no longer loads `subprocess` and `webbrowser` (now loaded only where a command uses them).
- **The MCP server is removed:** `mcp_server.py` and `docs/mcp.md` are gone. The plugin never registered it, and it was experimental. Agents other than Claude Code lose it. One that can run a shell command can still run the command line (see `docs/running.md`).
- **A smaller skill:** the `signoff` skill's `SKILL.md` loads whole each time the skill is used. It went from about 17 KB to about 9 KB. The less used fields of a round moved word for word to `fields.md` beside it. What to do once Signoff exits (the exit codes, the answers file, turning answers into actions) moved to `answers.md`. SKILL.md tells the agent when to read each, and now also says to put nothing secret in a board or an attachment.
- **Issue trackers:** in a project that keeps its tasks in an issue tracker, the `signoff-inbox` skill tells the agent to copy into the todo file only the issues that wait on you, each with its link, and to keep them in step. Signoff makes no call to the tracker.
- **Fresh pictures:** the screenshots in the docs and the README's page demo show today's page, with rounds in a sidebar, not tabs on top. `python3 media/demo/screenshots.py` now makes the screenshots as `record_page.py` makes the demo. Both run Signoff in a home of their own, so a running inbox on your machine no longer takes their run.
- **Short questions in chat:** the `signoff` skill tells the agent to ask a batch of up to four short questions with Claude Code's own question prompt, not on a page. Each question must be text only and not sensitive (no picture, board, attachment or marks), with 2 to 4 options. A bigger batch, or one with a picture, still goes on the page. Your own instructions still win.
- **Rounds whose run is gone stay in the inbox:** a project's open round whose Signoff run ended (Ctrl+C, the idle timeout) or died with its session, before you answered the round, left Waiting on you at once, and nothing showed it again. Now such an orphan round stays there for up to 14 days while no live run lists it and it has no outcome file. It counts in `state.json`, the band and the Dock badge, and the inbox writes its answers with the usual checks. Its row (**Run ended**) and its page say, in the round's language on the page, that the Signoff run that asked has ended and the answer goes to the project's sessions. A new run of the same rounds takes it on, under the same page. A run started just as the inbox started, whose round lock the inbox took first, now waits on the inbox instead of exiting 1.
- **The answer to such a round reaches the agent:** once every round of it is done (on its page or by another program), the inbox writes a request of the new kind `answer` in `requests/<project>/`. It holds the topic folder, the rounds and a fixed text of its own, and none of your answers. The project's open sessions get it through the plugin's mod, or the next session at its start. It reaches them as a message that asks the agent to tell you first, then read the answers and act. `signoff inbox done <id>` closes it. The round's Done banner says so instead of "the agent has them". The `signoff-inbox` skill says what to do with it, and an older plugin skips the new kind. The same request comes in two more cases. In the first, a waiter stops (SIGTERM, SIGHUP, Ctrl+C) or loses its stdout just after your Done in the inbox, before it handed the answers over. In the second, another program finishes the rounds just after their run, a waiter or a page run, stopped or timed out. A run's entry in `runs/` now notes its exit code (`exit`). The inbox writes the request once it lets go of rounds that are all done and whose newest run stopped (exit 130), timed out (exit 2) or died. A run whose start link was used twice (exit 1) gets none. An entry without `exit`, from an older plugin, counts as handed over, as before.
- **Commands on an item:** an item takes an optional `commands` key, 1 to 10 of `{text, lang, caption}`, for what the user must run before deciding. The round's page shows each under the item's description as the inbox shows a code block: its language, a **Copy** button that copies the text exactly, and a hint under a command that deletes with a relative path, whatever its language. Signoff never runs a command. Every code block now wraps, the inbox's too. A round fails to load in these cases. The command's text starts or ends with a space or line break (a trailing one runs on paste). It has more than 4000 characters or 60 lines. Its text, caption or language holds a known invisible or blank character: a control character other than tab and newline, a bidi override, a zero-width mark, a variation selector, the Braille blank, or an unassigned code point. A caption can hold an emoji. These checks catch the known tricks, so read a command before running it. The Markdown copy gives each command a line. An older Signoff refuses a round that uses the key, and so does an inbox it started (see **An inbox from before the update**).
- **Agent waits on this:** an item takes an optional `blocking` key, `true` or `false` (the default), for an item the agent's next step waits on. The round's page marks it after its title with a ■ and **Agent waits on this**, and its line in the sidebar with "agent waits", so the mark never rests on colour alone. The Summary gets a fourth filter, **Agent waits**, which shows only those items and appears only when one is marked. Any other value makes the round fail to load. The answers file and the Markdown copy do not change. An older Signoff refuses a round that uses the key, and so does an inbox it started (see **An inbox from before the update**).
- **A number item:** `"select": "number"` with a `range` key (`min` and `max`, from -10^15 to 10^15, optional `step`, default 1, and `unit`) asks for a number, such as a budget or a share, instead of made-up buckets. It has no `options`, and its `recommended`, a number in the range and on its step, is required. The round's page shows a slider and a number field that move together, the unit beside them, the recommendation preselected and tagged. A typed value between two steps goes to the nearest one when you leave the field, and the digit keys pick nothing there. The answer's `choice` is a JSON number (`0` included), `_skip` when the item is `skippable`, or `null`. Every other value, NaN and Infinity among them, is refused on every save. The Summary and the Markdown copy show the value and its unit, and the Markdown copy says whether it was the recommendation. An older Signoff refuses a round that uses it, and an answers file holding a number, and so does an inbox it started (see **An inbox from before the update**).
- **A context line:** a round takes an optional top-level `context`, one line of up to 120 characters in which the agent says which session asks and what it was working on (`feat/parser session: splitting the tokenizer`). The round's page shows it as the first line of the round (on a phone in Focus, with the first item only), and its row in Waiting on you shows it after the tab and in its open row, where the search finds it. A longer value, a line break, a tab or any other control or invisible character makes the round fail to load. Nothing is cut. The `signoff` skill tells the agent never to put a prompt, a transcript, a secret or a path there. The answers file, the Markdown copy, the panel's rows, notifications and `state.json` do not change. An older Signoff refuses a round that uses the key, and so does an inbox it started (see **An inbox from before the update**).
- **An inbox from before the update:** an inbox keeps running when you update the plugin. One that an older Signoff started refuses a round that uses a key it does not know (`commands`, `blocking`, `stakes`, `irreversible`, `settled`, `select: "number"`, `context`, `lines`, an attachment's `open`) or a `.diff` or `.patch` attachment. It says so only in its own log, so a run waiting on it would wait for good while you saw nothing. To prevent that, a waiting run now checks that some process holds the round's lock. It checks once an inbox from 0.4.0 or later has looked at the runs twice since the run started (a few seconds). The inbox locks each round it takes in, unless another run holds the lock already (the inbox then shows the round read only) or the file system cannot lock. A waiting run also checks its pictures and boards at start, as a page run does, so a bad one fails up front with its own error. When no one holds the lock, the run says on stderr that the running inbox did not take the round in. It tells you to restart the inbox (`signoff inbox stop`, then `signoff inbox open`) and run the same command again. It exits 1 with nothing on stdout, and the `signoff` skill has the agent tell you. In these cases the run keeps waiting as before: an inbox that does not look at all, a round another run holds, a file system that cannot lock, an inbox started again in between (its looks count afresh), or a run whose entry in the Signoff home could not be written. An inbox from 0.3.0 does not touch `inbox.lock`, so the run waits there too. After updating from 0.3.0, restart the inbox yourself.
- **The Markdown copy renders nothing:** these were still live in a GFM viewer: a character reference such as `&amp;`, `~~strikethrough~~`, a bare URL or `www.` address, a lone `-`, `+` or `=` line, a line such as `:-:` (a table without pipes), and a heading's closing `#`. A `%%` (in `for %%f`, say) began an Obsidian comment that hid the text up to the next one. A bidi override or zero-width character went through as it was. Now they are escaped, and a control, format or lone surrogate character shows as its code, such as `U+202E`. No Markdown escape stops two things. A GFM viewer still links an email address, and GitHub still renders its own extensions (`$math$`, `:+1:`, `@user`).
- **Stakes, cannot be undone, settled earlier:** an item takes three optional keys. `stakes` (`low`, `medium` or `high`) shows in the margin as a chip with a glyph and a word (▲ High stakes, ● Medium stakes, ▼ Low stakes), and the sidebar marks a high one. `irreversible` is one line of up to 200 characters that says why the decision cannot be undone. It shows in the margin as **Cannot be undone**, and the sidebar marks it. `settled` is one line that says where and when the user decided it before (`round-01, 11-14`). It needs `recommended`, the earlier decision. The item starts folded with that choice and a **Change** button, and it counts as decided while it holds that choice, so the inbox's panel does not wait on it. The Markdown copy gets a line for each key, and the answers file does not change. A bad value, or `settled` without `recommended`, makes the round fail to load. An older Signoff refuses a round that uses them, and so does an inbox it started (see **An inbox from before the update**).
- **No Vulnerabilities section:** the inbox no longer reads Uptick's `vulns.json` or `scan-repos.json`, and shows no vulnerabilities: the Vulnerabilities view, its rows, Hand to agent and Scan this project are gone, and the inbox never writes Uptick's scan list. A finding you handed over from 0.3.0 or 0.4.0 that the agent has not marked done still reaches it, as before.
- **No answer from a notification:** the macOS app's notification now only says how many wait, and a click on it opens the window. Accept & send and Other answer… are gone, and so are the control socket's `offer` and `accept`: an app from 0.3.0 or 0.4.0 gets the unknown-request reply for them and shows the number, and its `open` for an older banner opens the list. Answers files with `source: "notification"`, which those versions wrote, still load, resume and show on the past-decisions page.
- **No menu bar panel:** a click on the macOS app's menu bar icon now opens the app's window, as Open Signoff and a Dock click do, instead of the inbox in a small panel under the icon. The icon keeps the number waiting beside it, and a right click still offers Open Signoff and Quit Signoff.
- **Diffs and line notes in the format:** an attachment can now be a `.diff` or `.patch` file, with the same folder, path and size rules as `.md` and `.txt`. It takes an optional `open` (`true`: its box starts open). An item with attachments takes an optional `lines` (`true`: the user can note single lines of them). Its answer then holds `lines`, at most 50 notes of `{att, line, quote, comment}`. These are the attachment's index, the line's number in the file from 1 (split at each line feed, a carriage return at a line's end dropped), the line's first 300 characters, and the comment. A save checks each new or changed note against the file as read at start (400 otherwise). A note saved before is kept unchecked, so a file changed since never blocks a save, and a `quote` that no longer matches tells the agent the line moved. `sensitive` acts on an item with `lines`, Private hides the notes' comments, and the Markdown copy gives each note a line. The page takes the notes (see **Line notes on the page**), with a Private box on every item with `lines`. The box is ticked at the start on a `sensitive` one. An older Signoff refuses a round with a `.diff` or `.patch` attachment, `open` or `lines`. It also refuses an answers file with `lines`, and the past-decisions page shows that file as a broken round. An inbox it started refuses them too (see **An inbox from before the update**).
- **`signoff plan`, the plan review's command:** `signoff plan --topic <YYYY-MM-DD-plan-id> --folder <decisions folder> [--resume]` takes a plan on stdin (UTF-8, the white space at its end cut, then up to 256 KiB). It puts the plan on a fixed round, **Plan review**: one question, Approve the plan or Ask for changes, a comment and line notes, the plan attached and open, and no recommendation. It first closes the topic's older open rounds with an outcome file ("replaced by round-NN"). Then it writes `plan-NN.md` and `round-NN.json` in `<folder>/<topic>/`, each created new and never through a link. It waits on that round beside the running inbox, then prints the answers path. The new round's number comes after every file of a round's number in the folder, so an answers file left there (as `git clean -fd` keeps the ignored ones) never answers it. With no running inbox it exits 1 and writes nothing. Without `--resume` every call is a new round. With it, the newest round is reused only when it is the fixed round, its plan is the same bytes and its answers load as a run loads them. The plugin's mod runs the command when Claude Code leaves plan mode (see Plan review below). The agent never does. An inbox from before this version does not show the round. The command closes the round, exits 1 and says to restart the inbox.
- **The diff view:** a `.diff` or `.patch` attachment shows on the page as numbered rows: the old and the new line's number, the sign and the text. Added and removed lines have backgrounds of their own in every palette. These are two new colour tokens: the palette's green and red, and Rose Pine's foam and love. The sign is always shown and is read out as "added" or "removed". File and hunk headers stand apart. A file that is not a unified diff shows as numbered plain text. So does a `.md` or `.txt` attachment of an item with `lines`. Other attachments keep their plain box. A hunk counts only after a `+++` line. A file shows as plain text in these cases: it has no such hunk, a hunk has fewer lines than its `@@` counts, a hunk has a stray line inside, or a `+`, `-` or space line comes straight after a full hunk or its `\ No newline` line (a line starting with `+++ `, `--- ` or `-- ` aside). An attachment with `open` starts open, on a round's page and on the past-decisions page. The rows are drawn when the box opens (an open box: when its round is shown). The first screen comes at once and the rest in chunks, so a 256 KiB file of short lines keeps the page answering. A round you leave lets go of its rows; its open boxes draw them again from the top when you come back, with every note, typed or saved.
- **No monitor, so `/restart` works:** the plugin no longer declares a monitor. Its process never ended, so it made Claude Code's `/restart` refuse in every session. A message you send from the inbox (and the inbox's note on rounds finished after their run ended) now reaches an open session through the plugin's mod. The mod looks at the request folder of the session root's project through Claude Code's file reads. The session root is where the session started, or where `/cd` or a worktree move took it. A shell `cd` does not move it, as the monitor kept its project. Only for a request it has not handed over, the mod runs the new `signoff inbox requests <folder> <project> <id>…`, which prints the lines as one JSON line. The mod sends them as one prompt from the plugin. Claude Code runs that prompt as a turn of its own once the session is idle, after the turn that runs, and keeps what you were typing. After an Esc, Claude Code takes no prompt from a plugin until you send something. Such a message then goes at your next turn, as a turn of its own. This also works with the Waiting hint set to off, which now only hides the count. A reload of the mod sends nothing twice. After a `/clear`, a later session start with no other live session of the project hands over what still waits, as before. In `claude -p`, where the mod does not look, a message arrives only at a later session start with no other live session of the project. So do the older messages of a project the session's root moves into. The hooks note a session by its working folder. So after a shell `cd` into another project, the inbox can count the session there while its mod hands over the root's project's messages. After you update, restart the inbox (`signoff inbox stop`, then `signoff inbox open`) and every open Claude Code session. On Windows, where the inbox does not run, restart the sessions. An inbox started before the update does not know this version's new keys and control requests. A session that started on 0.4.0 keeps that version's monitor until you restart the session.
- **Line notes on the page:** on an item with `lines`, each attachment row leads with the line's number in the file. In a diff, it comes before the diff's own old and new numbers, which a phone leaves out to give the text room. Pressing the number (Tab, then Enter or Space) opens a field under that line with **Remove**. A second press goes back to the field, and Esc there goes back to the number. A line above the attachments says the numbers can be pressed. A field left empty saves nothing. An item takes up to 50 notes. Past that, the other lines' numbers are off, and that line says why. The notes save with the round in file and line order, each with its line's first 300 characters, counted as the server counts them. A reload shows them under their lines, in a box that starts open. A note whose line is gone, or whose line's first 300 characters changed, shows under the box, read only. It sits below "This file changed since. Line N said:" and the saved text in a box of its own. It goes back unchanged, so the save still passes, and the line takes a new note. Private covers the notes, and a `sensitive` item with `lines` starts Private. The Summary lists each note under its item (file, line and comment, hidden when Private). The past-decisions search finds their comments, but not a Private item's. A done round and the past-decisions page show the notes with nothing to press or type. In the numbered rows (a diff, or an item with `lines`), a carriage return, vertical tab, form feed, next line, line or paragraph separator inside a line now shows as `↵`, so you can see it. A number never wraps.
- **Plan review:** while the inbox runs, a plan waits on you in Signoff when Claude is about to leave plan mode in the main conversation of an interactive session. That means the terminal, the desktop app's Code tab or VS Code's panel. It was tried by hand in the terminal only. Once you press Done, the agent gets a message from the Signoff plugin, with none of your words. After Approve, that exact plan goes on once (see the next entry), and the approval is used up, also when the plan is rejected. After anything else, the agent reads your comment and line notes and revises. After an Esc, the message goes at your next turn, with a notice that your answer is saved. Five things end the review: `/clear`, `/resume`, quitting or restarting Claude Code, turning the Plan review setting off, and approving the plan in Claude Code's own dialog. Plan review is off by default. Turn it on with the new Plan review setting in `/config` (`plan`: `inbox`, and any other value is off). It does not run with `claude -p`, on Windows, for a subagent's plan, or for a plan over 256 KiB. It does not run either when the session's folder or the Decisions folder setting holds an invisible format or control character. `docs/running.md` says how it works.
- **An approved plan asks no second time:** after Approve in Signoff, the mod answers Claude Code's permission request for that plan, so plan mode ends with no dialog. Claude Code picks the mode, because the mod sets none. It is the mode from before plan mode, where measured (default, accept edits and auto). Bypass permissions was not tried. The Plan review round's text says so. The request names no tool call, so the mod binds it by time. It answers only the one request that meets all of these conditions. The request is for the exact approved plan, from the main conversation, with only the tool's known keys. It comes while the call the mod let through waits. No hook beneath the mod (your own settings hooks, other mods) gives a decision or a block, which goes back unchanged. Any other request gets Claude Code's own dialog. So does that call after a reload of the mod while it waits (the approval itself survives a reload, but not the one that turning the Plan review setting off causes). So does a call under a managed guard that runs no `classic` hooks of a mod (not measured). After a `/cd` into another project, the same plan is a new review there. Claude Code's own dialog applies where the inbox knows no project. An approval also needs the round's `plan-NN.md` to hold the plan the mod kept. Otherwise the answer is no approval, and a new review follows. A resumed review takes no answer from a round its topic folder already held when the review began. Three things end a kept approval, which otherwise waits as long as plan mode does. They are a rejection in Claude Code's own dialog (not an Esc there), a prompt outside plan mode, and turning the Plan review setting off. Whoever can write the answers or plan file, or get a start link of the inbox, can approve, and that now ends plan mode with no dialog.
